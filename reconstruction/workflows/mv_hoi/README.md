# MV-HOI workflow orchestration

This directory contains the OSMO workflows and host-side orchestration for
multiview human-object preprocessing, reconstruction, revalidation, QC export,
status publication, and intermediate cleanup.

Production state lives outside the repository. Source control contains workflow
definitions, orchestration logic, database migrations, and configuration
defaults; it does not contain credentials, the production database, generated
manifests, or campaign inventories.

## Layout

- `config.yaml`: dataset paths, workflow settings, concurrency, QC thresholds,
  pool order, export destination, and cleanup policy.
- `osmo/`: calibration, preprocessing, reconstruction, revalidation, export,
  export-retry, and engine-build workflow definitions.
- `orchestration/`: campaign controller, database API, query/export/status
  tools, cron wrappers, and cleanup worker.
- `alembic/`: the complete database upgrade chain. Existing revisions are
  immutable and must not be removed.
- `migration/`: supported database/weight migrations and the recovery tools
  still needed by active backlog campaigns.
- `tests/`: unit, workflow-structure, database, lifecycle, and integration
  coverage.

## Host setup

The submit host needs Python 3.10 or newer, network access to the production
database and object storage, and authenticated `osmo` and `aws` command
line clients. Image-version discovery uses `ngc` for an explicitly configured
`nvcr.io` registry, or `skopeo list-tags` for other container registries. OSMO authentication is configured through the approved local CLI
profile; it is not stored in this repository or generated by the bootstrap.

Bootstrap creates a private state directory, virtual environment, environment
template, generated-workflow directory, logs, manifests, locks, and database:

```bash
cd reconstruction/workflows/mv_hoi
python3 orchestration/host.py bootstrap
```

By default state is stored beneath
`${XDG_STATE_HOME:-$HOME/.local/state}/v2d-mv-hoi`. Override it with
`MV_HOI_STATE_DIR`. The generated `host.env` is private and must not be
committed.

Important environment settings include:

- `MV_HOI_DATABASE_URL` or `MV_HOI_DB_PATH`: authoritative database.
- `MV_HOI_CONFIG_PATH`: optional configuration override.
- `MV_HOI_VENV`: orchestration virtual environment.
- `MV_HOI_ALLOW_SUBMIT=1`: required on the single authorized submit host.
- `V2D_IMAGE_REGISTRY`: your container registry/namespace (also accepted as dataset
  `image_registry` or the submit/export CLI `--image-registry`).
- `S3_ENV`, `KRATOS_DRS_ENV`, and `HITL_AWS_ENV`: optional credential scripts;
  `CSS_ENV` remains a legacy alias for `S3_ENV`.
- `MV_HOI_REVALIDATION_CAMPAIGN` and `MV_HOI_BACKLOG_CAMPAIGN`: campaigns
  serviced by the managed cycle.
- `MV_HOI_VERIFY_PAYLOAD_HASHES=1`: verify export payload hashes during
  campaign reconciliation.
- `MV_HOI_QC_QUERY_ENABLED=0`: allow processing to continue while external QC
  querying is unavailable; export candidates remain waiting for QC.

Keep secrets out of `host.env`. It should point to private credential scripts:

- `S3_ENV` can export `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_ENDPOINT_URL`, and
  `S3_REGION`. Explicit `CSS_*` equivalents remain supported; `S3_*` takes
  precedence. Standard AWS profiles, environment credentials, and roles also
  work. With no endpoint override, `s3://bucket/prefix` and bare `bucket/prefix`
  use standard S3; `swift://host/account/bucket/prefix` uses the specified host.
- `KRATOS_DRS_ENV` exports the Kratos profile, namespace, warehouse, and
  service-account variables consumed by `export.py`.
- `HITL_AWS_ENV` configures the AWS CLI used to mark HITL batches ready.
- `STATUS_PUBLISH_ENV` configures the status-spreadsheet publisher.

Use `~/.pgpass` or `PGPASSFILE` for PostgreSQL authentication rather than
embedding a password in `MV_HOI_DATABASE_URL`. After editing the generated
template, load the host and CSS environments and run the read-only checks:

```bash
source "${MV_HOI_STATE_DIR:-${XDG_STATE_HOME:-$HOME/.local/state}/v2d-mv-hoi}/host.env"
[ -z "${S3_ENV:-${CSS_ENV:-}}" ] || source "${S3_ENV:-$CSS_ENV}"
python3 orchestration/host.py doctor --version 1.6.45
```

`doctor` checks configuration, submit authority, required clients, CSS access,
database revision/integrity, and the requested immutable image release. It
only verifies that the OSMO binary exists, so verify authenticated OSMO access
separately before enabling submissions. Do not set `MV_HOI_ALLOW_SUBMIT=1` on
more than one host.

### Images, weights, and TensorRT engines

OSMO uses the registry images named by the workflow release, not whatever
Docker images happen to exist on the submit host.

The OSMO MV-HOI pipeline has been validated on NVIDIA H100, L40, and L40S
GPUs. Other NVIDIA GPU families are not currently documented as validated.
TensorRT engines must match the target GPU architecture and runtime.

When module code changes, build the affected image locally and validate it
before publishing:

```bash
./build_images.sh                    # all MV-HOI images
./build_images.sh foundation_pose   # one image
```

Registry publication is an explicit, externally visible release operation and
requires authorization:

```bash
./push_images.sh <new-semver> -m "<release reason>"
```

Do not create a new image version for orchestration, workflow-YAML,
configuration, or documentation-only changes when the container contents are
unchanged. `host.py doctor --version <semver>` verifies that every managed
image alias for a release exists before campaign submission.

Model assets live under the configured versioned `weights_base_url`. Use
`migration/migrate_weights_to_css.py --help` for general weight publication.
Foundation Stereo and FoundationPose TensorRT engines are architecture- and
runtime-specific. If a weight release lacks engines for a target GPU, submit
the reviewed `osmo/mv_hoi_build_engines.yaml` once to that pool with the exact
image tag and weight-release URI. For the configured L40 pool, the command
shape is:

```bash
osmo workflow submit osmo/mv_hoi_build_engines.yaml \
  --set workflow_name=<unique-name> \
        image_tag=<semver> \
        image_registry="$V2D_IMAGE_REGISTRY" \
        weights_base_url=<versioned-weights-uri> \
  --pool <your-pool>
```

Verify one nonempty Foundation Stereo
`*_sm_8_9.engine`, two nonempty FoundationPose `*_sm_89_fp32.engine` files,
their hashes, and the unchanged ONNX/manifest inputs before routing production
work there. Submissions use normal priority unless `MV_HOI_HIGH_PRIORITY_POOL`
explicitly selects one of your pools for `HIGH` priority.

## Database and lifecycle

SQLite is supported for local development and migration evidence. PostgreSQL is
the production backend. `db.init_db()` validates the database and upgrades it
to `database.ALEMBIC_HEAD`; it refuses legacy `pipelines` databases and
obsolete generic `stage_runs` schemas.

The normalized model separates:

- immutable workflow executions and stage-run attempts;
- durable stage requests and retry lineage;
- frozen campaign identities and membership;
- sequence dependencies, human QC reviews, export authorization, and cleanup
  jobs.

Terminal attempts remain history. A retry is a successor request rather than a
mutation of the failed attempt. At most one active request may exist for the
same campaign, sequence, and stage.

Public lifecycle rows intentionally summarize several normalized tables.
Examples include `WAITING_LABELS` for blocked reconstruction requests and
`WAITING_QC` for completed reconstruction outputs without an accepted review.

Supported migration entry points:

```bash
python3 migration/migrate_processing_db.py --help
python3 migration/migrate_sqlite_to_postgresql.py --help
python3 migration/migrate_weights_to_css.py --help
```

Keep the full Alembic revision chain even after every deployed database reaches
head; new databases and recovery snapshots still upgrade through it.

## Frozen campaigns and dynamic requests

A campaign is created as a draft, then frozen with:

- an immutable inventory URI and SHA-256;
- an immutable configuration URI and SHA-256;
- an expected membership count and output root.

Inventory records are frozen initial task entries. They contain sequence
identity, route, priority, source-object identities, and adopted lineage where
applicable. Later stage requests are generated dynamically from verified
upstream results, while database foreign keys retain the full lineage.

`frozen` means the campaign cannot silently change inventory, configuration,
membership, or destination. Replacement policy requires a new campaign; normal
attempt and retry rows continue to be created within the frozen campaign.

Common read-only commands:

```bash
python3 orchestration/campaign.py status
python3 orchestration/campaign.py status <campaign>
python3 orchestration/campaign_report.py <campaign>
```

### Creating a fixed-inventory campaign

Generate and audit the candidate inventories before creating a production
campaign:

```bash
python3 orchestration/campaign_inventory.py \
  --dataset sc_office_4exo_1 \
  --output-dir /absolute/path/to/audited_inventory \
  --content-hashes
```

The builder emits the cutover inventory, separate revalidation/reprocessing
inventories, and request-sized revalidation records. Review membership,
routes, priorities, adopted preprocess lineage, source identities, and counts.
Prepare the matching reviewed configuration JSON, then upload both files to
new immutable CSS object names. Never overwrite an artifact already referenced
by a campaign.

The normal fixed-inventory sequence is create, freeze, and enqueue:

```bash
python3 orchestration/campaign.py create \
  --name <campaign-name> \
  --type BACKLOG_REPROCESSING \
  --dataset sc_office_4exo_1 \
  --version 1.6.45 \
  --output-uri <data-export-3-root>

python3 orchestration/campaign.py freeze <campaign-name> \
  --inventory /absolute/path/to/backlog_reprocessing_inventory.json \
  --inventory-uri <immutable-css-inventory-uri> \
  --configuration /absolute/path/to/configuration.json \
  --configuration-uri <immutable-css-configuration-uri>

python3 orchestration/campaign_controller.py enqueue <campaign-name> \
  --inventory /absolute/path/to/backlog_reprocessing_inventory.json
```

Use `LEGACY_REVALIDATION` and its matching inventory for revalidation. The
freeze command records local file hashes alongside the immutable URIs;
`enqueue` refuses a mismatched hash, dataset, campaign type, count, or duplicate
sequence. Inspect `--help` for canary approval, campaign completion, successor,
and narrowly scoped recovery commands. Production mutations require explicit
submit authority and reviewed artifacts; do not use manual `submit.py --force`
as a substitute for campaign lifecycle operations.

The campaign controller refreshes OSMO state, repairs bounded infrastructure
failures, advances dependency-ready requests, dispatches within configured
limits, publishes accepted canary outputs, schedules cleanup, and reconciles
campaign progress:

```bash
python3 orchestration/campaign_controller.py cycle \
  --revalidation-campaign <name> \
  --backlog-campaign <name>
```

Queue order is priority descending, then creation time and request ID.
Infrastructure retries preserve campaign membership, source manifests,
upstream lineage, and queue priority.

For backlog reprocessing, the normal lifecycle is:

```text
preprocess -> WAITING_LABELS -> reconstruction -> WAITING_QC -> export
```

Preprocessing may be fresh or may adopt a validated complete result frozen in
the inventory. Reconstruction is blocked until the four left-camera manual
label JSON files and their manifest identity are present. Human QC is bound to
the exact successful reconstruction attempt; a different reconstruction needs
fresh QC. Only dependency-ready requests enter the dispatch queue. The public
tracker projects these database relationships as lifecycle labels rather than
copying one request row verbatim.

### Refresh and retry semantics

Each campaign cycle performs one OSMO refresh pass. It does not sleep or poll a
workflow repeatedly within the same cycle. A submission that OSMO temporarily
reports as missing remains `UNKNOWN` until ten minutes have elapsed from its
persisted submission time. A later cycle then records an ordinary `FAILED`
attempt and sends it through the shared infrastructure-retry path.

The shared policy allows two retries after the original execution. Successors
become eligible 10 minutes after the first observed failure and 30 minutes
after the next observed failure. Cron timing, concurrency, and pool capacity
can make the actual submission later. A third failed execution is terminal.
Retries are new requests; failed requests and workflow executions remain
immutable history, and repeated refreshes cannot create duplicate successors.

Retryable roots include recognized OSMO backend, scheduling, node, image-pull,
network, and control-plane failures. Root task logs are also checked for
`FileNotFoundError` and “No such file or directory” signatures when OSMO has
not already supplied an infrastructure classification. `FAILED_UPSTREAM`
tasks are ignored when identifying roots, and every root failure must be
retryable. The separate OSMO submission-not-found response uses the ten-minute
rule above rather than the file-not-found classifier.

## Workflow behavior

### Calibration and preprocessing

`mv_calibration.yaml` creates calibrated camera parameters.
`mv_preprocess.yaml` validates source data, anonymizes videos, builds the
object prompt/mesh inputs, and prepares reconstruction assets.
`mv_preprocess_oneoff.yaml` remains available for explicitly requested
standalone preprocessing.

An OSMO `COMPLETED` status is provisional for preprocessing. Before recording
success, orchestration lists the remote output and requires nonempty metadata,
EDEX, aligned mesh, all eight camera image HDF5 files, and all eight camera
videos. An incomplete upload or an unavailable CSS listing is recorded as an
infrastructure failure and follows the same bounded retry policy. This guards
against a successful compute task followed by a failed OSMO output upload.

The legacy `object.bbox` field in source `hoi_metadata.yaml` is deliberately
ignored and removed from forwarded metadata. Preprocessing never converts it
into labels. It forwards a nonempty `object.prompt` to `prompt.txt` for the
Grounding DINO path. Manual labels are separate artifacts under
`mv_preprocess/labeled_bboxes/` and are never derived from source metadata.

### Reconstruction

`mv_hoi_reconstruction.yaml` runs depth, human/object masks, FoundationPose,
SAM3D Body/SOMA, ground-plane estimation, metric evaluation, accuracy checks,
overlay rendering, and HITL upload.

`check_accuracy` has nominal dependencies on `export_soma`,
`estimate_ground_plane`, and `export_fused_pointcloud`. Their outputs are not
metric inputs, but every task must succeed before accuracy and HITL upload can
proceed.

Object-mask seeding has two explicit sources. Campaign reconstruction uses
`mv_preprocess/labeled_bboxes/*.json` when
`object_bbox_source.txt` contains `manual_labeled_bboxes`; Grounding DINO is
skipped. The noncampaign fallback has no marker and requires `prompt.txt`, then
uses Grounding DINO output. `validate_labeled_bboxes` verifies the frozen label
manifest and schema before manual labels can be consumed.

Continuous rotational symmetry defaults to 10 degrees. Objects with two or more
centered, nonparallel continuous axes use unrestricted-rotation mode with a
stable reference rotation and normally estimated translation.

### Revalidation

`mv_hoi_revalidation.yaml` evaluates frozen legacy reconstruction outputs,
retains the unchanged FoundationPose comparison gate, generates current
accuracy evidence, merges automatic and existing human-QC failure segments,
applies interaction trimming, and stages the export.

`mv_hoi_revalidation_export_retry.yaml` is only for verified revalidation
artifacts that contain every required upstream manifest. Otherwise rerun the
full revalidation workflow.

Revalidation failures are not automatically transferred to a reprocessing
campaign.

### Accuracy and human QC

The reconstruction DAG still computes the single labeled-frame object-mask
containment diagnostic. For each camera it uses the first frame key in the
manual label JSON (normally frame 0), compares the SAM2 mask bbox with the
label bbox padded by 10%, and reports average containment against 0.8. The task
runs in report-only mode: `FAIL` or `INCONCLUSIVE` is retained in
`check_accuracy.v3` but cannot reject a sequence. Malformed label manifests or
task inputs remain workflow errors.

Human and object metrics are evaluated independently:

- Chamfer hard-fails only when the pooled median is strictly above 40 mm.
  Per-view diagnostic segments are emitted for distances strictly above 50 mm
  for at least five consecutive source frames.
- Silhouette bounding-box containment marks frames below 0.8. A subject
  hard-fails only when its unioned failure segments cover strictly more than
  50% of the sequence.
- Both masks discard tiny noise before containment. Rendered silhouette boxes
  are padded on each axis by `max(8 px, ceil(10% of the bbox dimension))`.
- Skipped source frames break continuity. Segments are deterministic, 0-based,
  half-open intervals.

Chamfer segment count/coverage and combined automatic segment statistics are
diagnostic only. Export merges automatic metric segments with human-QC
segments. The human-QC gate remains independent and uses the configured maximum
of 10 annotations and 50% coverage; equality passes.

### Export and trimming

Committed production exports are written beneath the configured
`data_export_3/<sequence>/` destination. Request-scoped work is staged under
the configured work prefix, validated, and published with `commit.json` last.

The retained interaction interval is:

```text
[3 seconds before first stable proximity, 3 seconds after last stable proximity)
```

Stable proximity means human-object distance at or below 10 cm in at least five
of seven frames. If no stable interaction exists, the full sequence is kept.
Every temporal payload uses the same interval. Human and automatic failure
segments are intersected with it, segments outside it are dropped, and retained
indices are rebased while preserving half-open semantics.

Export commits retain compatibility with historical report versions needed to
read already persisted evidence. Do not remove v1/v2 readers merely because
new writes use newer schemas.

## Configuration

`config.yaml` is a public deployment template. Copy it outside the repository,
set `MV_HOI_CONFIG_PATH`, and supply `swift_base` (S3, Swift, or bare bucket path),
`mesh_base`, `weights_base_url`, `image_registry` (or `V2D_IMAGE_REGISTRY`),
`hitl_s3_base`, and `osmo_pools`. OSMO data credentials and licensed model assets
must be configured by the deployment owner. The repository does not provide a
hosted registry, storage account, pool, or HITL service.

The template retains the release's pipeline stages, resource requirements,
QC thresholds, export schema and campaign controls. Intermediate paths remain
`data_output`, and committed exports use `data_export_3`. Automatic cleanup is
disabled. Enabling it requires an explicit campaign allowlist and export cutoff;
inspect the dry-run and cleanup canary before enabling deletion.

Kratos is an optional provider integration, excluded from `requirements.txt`.
If your deployment uses Kratos for human QC, obtain and install a compatible
`kratos-cli` from your provider's package source (the integration was tested
with 4.0.158), authenticate it, and configure `kratos_table`,
`kratos_status_table`, and a positive `kratos_project_id` in the export workflow.
Also provide the profile, namespace, warehouse and service-account settings
listed above. No public replacement is bundled. Without the integration or
completed human QC evidence, affected exports remain `WAITING_QC`; automatic
quality gates are still enforced. Local reconstruction and other orchestration
commands do not require importing Kratos.

Direct OSMO submissions must pass `--set image_registry=$V2D_IMAGE_REGISTRY` and
all required storage inputs. Publish your locally built MV images with
`V2D_IMAGE_REGISTRY=registry.example.com/your-team ./push_images.sh`; immutable
release checks verify that every managed image contains the requested version.

Campaigns reference frozen copies of inventory and configuration artifacts.
Editing `config.yaml` does not retroactively change a frozen campaign.
Accordingly, inspect the campaign's frozen configuration before assuming the
checkout defaults are its live limits.

## Managed cron

Install or inspect the managed block through `host.py`:

```bash
python3 orchestration/host.py install-cron
python3 orchestration/host.py install-cron --apply
```

The optional schedule generated by `host.py install-cron` runs:

- campaign cycle at minutes 0 and 30;
- asynchronous cleanup at minutes 5, 15, 25, 35, 45, and 55;
- HITL-ready marking at minute 50;
- status publication at minutes 10 and 40.

Inspect `crontab -l` before maintenance and preserve the installed block unless
the schedule change itself is authorized.

`campaign_cron.sh` holds a nonblocking host lock, so overlapping cycles exit
without work. It performs one OSMO refresh pass per cycle; persisted submission
times carry ambiguity grace periods across later cycles.

`publish_status_cron.sh` publishes the current database view and does not
perform a campaign refresh. `export_cron.sh` is retained for possible
campaignless mainline operation but is not part of the managed cron block.

## Querying and status publication

```bash
# Active-campaign lifecycle summary
python3 orchestration/query.py --dataset sc_office_4exo_1 --summary

# One campaign
python3 orchestration/query.py --dataset sc_office_4exo_1 \
  --campaign <name> --summary

# One sequence's attempt history
python3 orchestration/query.py --dataset sc_office_4exo_1 \
  --pipeline mv_hoi_reconstruction --sequence <sequence>

# Dry-run the sheet payload
python3 orchestration/publish_status.py --dataset sc_office_4exo_1 --dry-run
```

The published lifecycle sheet is a public projection, not a one-to-one dump of
database tables. It includes request stage/status and blocked reason so humans
can distinguish `WAITING_LABELS` from `WAITING_QC`.

## Cleanup and recovery

Automatic intermediate cleanup is driven by durable cleanup jobs and the
campaign allowlist in `config.yaml`. It preserves validated export commits,
metrics, labeled boxes, videos, mesh/provenance, and cleanup evidence. The
worker is read-only unless `--apply` is supplied:

```bash
python3 orchestration/cleanup_intermediates.py --help
```

The following campaign-specific tools remain temporarily because active backlog
campaigns can still require their recovery semantics:

- `cleanup_backlog_pending_intermediates.py`
- `cleanup_backlog_stale_intermediates.py`
- `cleanup_backlog_legacy_flat_intermediates.py`
- `reset_backlog_campaign.py`

Re-audit these tools after the active backlog reprocessing campaign is
terminal. Completed revalidation does not require them.

## Validation

From this directory, using the host orchestration environment:

```bash
python3 -m compileall -q orchestration migration tests
python3 -m pytest -q
```

Workflow definitions should also be YAML-parsed, shell wrappers checked with
`bash -n`, and production changes reviewed to ensure configuration, workflow
DAGs, Alembic head, and managed cron entries are unchanged.
